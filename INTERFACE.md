# Integration interface

This repository owns the Bambu-only MCP server, its tools and Bambu printer, slicer and native-helper integrations. It does not own printer firmware, Bambu account services, installed vendor software or client applications.

## MCP and agent discovery

Clients connect over stdio or streamable HTTP. Stdout carries only MCP protocol messages; diagnostics go to stderr. Tool definitions and schemas describe their arguments and model-specific availability. `get_agent_guide` serves a task index and focused topics, including signing and printing, to tools-only clients; `bambu://workflow/` resources serve the same guide text. The signing guide supplies optional configuration descriptors, including a secret marker, without configured values. `get_agent_readiness` returns local configuration and capability states, named blockers and next actions with `dispatch_authorized: false`; it performs no live printer or physical readiness check.

Streamable HTTP uses one process-owned backend and transient protocol contexts for active requests, with no resident idle client session map. Legacy initialization returns client-held HMAC-signed compatibility metadata containing protocol version, capabilities, client information and a nonce. It is not an idle lease: restarting the process rotates its signing key and invalidates old tickets. `GET` and `DELETE` return 405 with `Allow: POST, OPTIONS`; DELETE does not revoke a ticket. Request cancellation or connection loss revokes the affected active operation's authority, not the shared backend or its job monitor.

The modern HTTP path uses the MCP SDK's native request handling. An opaque, signed, one-use continuation retains only active operation state during human input, with a 10-minute input wait and 30-minute operation deadline; confirmation resumes the same handler, never replays the physical operation. Both protocol paths share a 128-active-operation bound and reserved control capacity. After abort, handlers have 30 seconds to settle before fail-stop if they do not cooperate; this does not prove a dispatched mutation was undone. Shutdown waits up to 4.5 seconds for actual handlers before backend cleanup; otherwise the process exits with outcomes potentially unknown. No per-agent backend or additional service is required.

HTTP validates Host, Origin and optional static bearer authentication and bounds request bodies. OAuth authorization, token validation and discovery, TLS termination, and a secure proxy are deployment responsibilities; the server is not an OAuth provider. Non-loopback requires bearer authentication and separate TLS protection. An explicit Host allowlist is recommended for every non-loopback bind and required for hostname or wildcard binds; a literal IP bind otherwise enforces its exact Host. `MCP_HTTP_STATEFUL` must be absent or false; true and invalid boolean values fail startup. `MCP_HTTP_JSON_RESPONSE` prefers JSON for initialization and discovery while interactive calls can use SSE.

`bambu-printer-mcp-http-client` is a legacy stdio-to-HTTP relay using a private bearer-token file and HTTPS or loopback HTTP; it never starts or cleans up the backend. It declines `server/discover` so the host can fall back to legacy discovery. The relay retains a bounded initialization contract and, after a confirmed 404, may reinitialize and retry only discovery lists or ping when safe. It never automatically replays `tools/call`; check state before manually retrying an uncertain operation. Authentication and capacity errors use sanitized diagnostics.

`counterpart/1` remains a separate existing contract. The existing `counterpart_setup_fields` schema and field roles are unchanged. Changes to public tools, printer models, status semantics or `counterpart/1` require owner review and downstream impact analysis.

## Separate Orca workspace

The separately owned Orca service can be exposed through an authenticated proxy and a private Unix socket. It targets the official `feature/mcp` source at `8cccdf82d00381942d9b664750457da318e7d068`, including X2D profiles and full upstream MCP tools. Its separate image and upstream license do not change the printer server's ownership or license. The container uses `network_mode: none`; it receives no printer credentials and cannot directly reach a printer. Authentication and TLS belong to the proxy, and the gateway uses its own private bearer token.

`workspace_create` returns a durable opaque ID without starting a GUI. `workspace_open` selects that ID for the single GUI worker; native calls include the ID. `workspace_status` reports the worker and known workspace state, and `workspace_close` attempts a verified checkpoint before releasing the worker. IDs, profile data and artifacts persist across client and server restarts; an unclean stop or failed checkpoint requires recovery rather than an assumed restore. There are no per-agent protocol sessions. Workspace IDs coordinate one trusted operator and are not tenant-security boundaries. Expiry revokes access; unfinished outcomes remain unknown and are not replayed. Exclusive socket ownership and shutdown settlement prevent another worker from starting while the previous one is still owned.

The candidate owns a private D-Bus session with the GUI worker. Its internal launch identity is a session runner; this interface does not expose or guarantee a GUI process ID. An isolated actual-image trial verified the process topology, two clean closes and a same-ID restore.

An isolated runtime trial reached readiness, sliced an X2D fixture and separately completed checkpoint, same-ID restore and cleanup. A fresh-client authenticated slicer invocation remains unverified. See [deploy/orca/README.txt](deploy/orca/README.txt) for configuration and validation limits.

## Printer operations and optional authentication

The explicit `connection_mode: "signed_mqtt"` print route uses inspected 3MF projects, including `.gcode.3mf`, and an operator-configured signer plus an absolute `BAMBU_PRINTER_TLS_CA_FILE` for direct printer storage TLS. It checks capability and a unique internal-storage name, uploads and requires a terminal acknowledgement, then reads the file back and checks its size and SHA-256 against the checked local artifact before final fresh preflight and signed MQTT dispatch using the selected local or cloud writer. Unsupported capability, mapping, trust or transfer fails closed. No automatic print replay, route fallback or file deletion is promised; post-publication failures can leave dispatch uncertain. `upload_file` provides 3MF upload-only on this route; `upload_gcode`, a raw G-code API, refuses it. Legacy routes retain their own formats. Model and firmware support is capability-dependent, not universal. Focused fixtures and one private X2D trial support this route: upload readback matched, and a signed-cloud job on firmware 01.02.00.00 reached FINISH with camera evidence of first-layer deposition and the completed fixture on the plate. Hands-on physical quality and fit remain unverified; other models and firmware are not qualified. This does not qualify the separate native-helper route. The four-client audit remains required before an upstream PR.

`get_agent_readiness` describes the default signed print selection and whether an absolute CA path is configured; it does not validate that file, a TLS session or physical readiness. A per-call route can differ from the default.

`get_printer_status` defaults to bounded allowlisted compact monitoring state, progress, temperatures, reported slots and error codes, with missing values null and no raw payload. This changes the earlier default: existing clients requiring the legacy full response, raw telemetry or the structured response must explicitly request `detail: "full"`. Compact mode returns one JSON text block for text-only and structured-aware clients, without a duplicate structured copy. Compact status is not a safety preflight and slot data may be incomplete. `get_printer_status` preserves display status when `fresh` is omitted or false. With `fresh: true`, it uses the shared backend to request new MQTT status and version reports and requires observed model identity and a printer-returned serial matching the configured target. Full detail returns `observedSerial`, raw telemetry and request/receipt timestamps; compact detail returns verified identity evidence and timestamps without the serial or raw telemetry. Missing identity, mismatched serials and timeouts fail without cached or configured identity substitution. This read-only telemetry is not complete print preflight or dispatch authorization.

Printer status and commands use MQTT; supported file transfers use FTPS or a separate native route. Printing retains inspection of the exact dispatched snapshot and selected plate, fresh printer safety checks and existing human-authorization semantics. Upload and dispatch are separate; a publisher acknowledgement or helper receipt does not establish device acceptance or physical success. Uncertain dispatches are not automatically replayed.

For a mixed-nozzle X2D plate, inspection uses the complete selected-plate physical-extruder map to compare and return nozzle arrays in firmware ID order. A scalar first-extruder diameter requires a single selected filament with a corroborating logical extruder binding. The full nozzle declaration and all live preflight requirements still apply. Incomplete or contradictory required mappings reject the file.

Fresh safety collection has an overall 15-second deadline covering connection and concurrent disconnection; both the MQTT transport connection timeout and its outer connection deadline are 10 seconds, disconnection drain is bounded to 5 seconds, and collection to at most 5 seconds of the remaining budget. Typed MQTT connection failures carry allowlisted `connection_diagnostics`; native and bridge print failures from their initial or confirmation safety reads also identify `safety_stage`. These diagnostics do not expose credentials or raw transport messages, and they do not trigger a retry. Native helper execution defaults to 230 seconds, with kill escalation after one second. These limits do not bound preceding slicing or inspection. Monotonic expiry prevents late asynchronous safety completion from recording or authorizing a dispatch; bookkeeping occurs synchronously at the final authorization boundary. Existing errors retain bounded, allowlisted `native_diagnostics` and preserve stable known refusal codes when available. Success requires an exact, unambiguous successful receipt for the latest authorized attempt. A client deadline or missing helper receipt does not establish whether dispatch occurred; a missing or pruned flight record is inconclusive. Failures after authorization remain uncertain unless there is an explicit rejection, and uncertain dispatches are not automatically replayed.

Signed controls are opt-in with explicit local or cloud transport and require an imported or explicitly provisioned application key, certificate chain and current CRL, independently configured device CA, OpenSSL 3 and a private initialized persistent sequence store. Optional local broker TLS trust is a separate boundary. Selected signed controls fail closed if prerequisites fail; signed project dispatch does not upload files, and legacy `gcode_file` dispatch is blocked on that route. The typed LED protocol has its own deterministic unsigned route, not a fallback from failed signing. Counter reservations cover only processes using the same store, not other applications or hosts.

Optional app-package provisioning recognizes only the exact reviewed Handy APK and extracts its identified bootstrap locally. The source can acquire that exact official package automatically; this acquisition has not been live-qualified. Provisioning makes a fixed-host regional issuance request without account credentials and validates the returned bundle with the existing pin, key match and issuer CRL policy. Complete managed generations are published atomically under an OS-held lock. Operator-edited files outside the managed writer are not covered by its concurrency contract. Legacy direct PEM directories remain supported. Setup does not initialize, replace or reset sequence state. The package and embedded bootstrap are not distributed in this repository. See [provisioning](docs/signing-provisioning.md) for source attribution and current integration limits.

`connection_mode: "signed_cloud"` is separately enabled by `BAMBU_CLOUD_PRINT_ENABLED=true`; it can coexist with the selected signed MQTT write transport. It uploads the exact checked snapshot and selected plate, then reruns fresh printer preflight immediately before the cloud task POST. The route uploads a selected-plate configuration 3MF and preview first, then the unchanged full print 3MF; server cover processing is unconfirmed. That POST starts the print and creates its history record; no additional MQTT dispatch occurs. Account login and application proof are both required. Mutations are not retried; a failed or missing dispatch response requires reconciliation with the printer and history before another deliberate attempt. Source and mocked normal-entrypoint coverage do not establish live cloud dispatch or universal firmware compatibility.

`get_printer_filaments` reports AMS and external trays from display MQTT state; it may be cached or incomplete and missing identifiers do not prove an empty holder. `account_list_filament_inventory` reads the Bambu account cloud library as a separate source, including manually added reels. It uses bounded pagination when a total is reported, and otherwise reads one bounded native catalogue response. Retrieval completion is not an atomic snapshot or independently verified account count and returns nullable reported gram weights; these are not verified physical measurements. `get_filament_inventory` adds unified `spools` for every account record, while preserving `printer`, `library` and `matches`. Unique unmatched printer UUIDs are separate observations that may overlap library reels and are not added to stock rows. It links only a unique nonzero 32-hex cloud RFID to a unique reported tray UUID; matched printer reports take precedence with conflicting account reports flagged. Unmatched account `inPrinter:false` reports `not_loaded`; `inPrinter:true` reports `loaded` with account evidence, and missing or ambiguous evidence remains `unknown`. Account and printer quantities remain separate. Unidentified loaded holders are listed separately and never counted as distinct reels; coverage records source availability without claiming a total unique physical count. The library may be unavailable while printer observations remain visible. Optional account-reported location is retained separately with unguaranteed freshness; it does not establish a printer match or override MQTT. An account-reported `not_loaded` state does not prove physical removal, movement or storage location. The account list uses a complete explicitly configured signed-cloud credential tuple first, with a recognized regional broker; partial tuples fail. Without an explicit tuple it uses the private cached account session. It exposes no credentials. The cloud endpoint is undocumented and may change; see [Bambu Studio's cloud client](https://github.com/bambulab/BambuStudio/blob/master/src/slic3r/GUI/fila_manager/wgtFilaManagerCloudClient.cpp) and [independent protocol research](https://github.com/scarlton/open-bambu-networking/blob/master/NETWORK_PLUGIN.md#615-filament-manager-cloud-spool-catalogue).


`account_reprint_cloud_task` requests an owned, successful, printable completed job on the same configured printer. It requires `task_id`, `confirm_original_job_reference: true`, cloud-print and signed-control configuration, account binding and application proof. Optional `current_mapping` is an array of `{filamentId, ams, amsId, slotId}` integer rows, one per used original filament; it selects current slots and cannot select a nozzle. The original nozzle is derived from the original job, while fresh printer identity, model, nozzle, materials, slot mapping, idle and error checks and physical confirmation remain required. A selection is not proof that current hardware matches.

For fresh physical verification, AMS assignments require explicit fresh occupancy evidence. An external manual holder requires a unique fresh slot/type match and physical confirmation; that evidence is not RFID occupancy proof.

`account_reprint_hold` accepts `action: "status"`, `"observe"`, or `"recover"`; recover also requires `acknowledge_review: true` and interactive human confirmation after reviewing the printer and account history. The canonical-serial pending hold is durable across restart and gates new print starts and resume; stop and heater-off remain available. Because a stable collector connection epoch is unavailable, neither idle nor terminal telemetry clears a hold automatically. Recovery checks account binding, fresh idle and error state, cancellation and the exact hold nonce under the relevant locks. Recovery sends no printer command.

This is a distinct provider-reference route, reported as `provider_completed_job_reference`: it does not reslice, inspect original G-code or prove its byte identity. Unsupported or insufficient original evidence requires the original sliced file; conflicting historical assignments require a valid current mapping. It revalidates the reference and sends at most one task POST, with no second MQTT print or automatic retry. An uncertain handoff requires reconciliation. File-based routes retain their exact-snapshot inspection policy. This route has not been live-qualified.

Optional account tools provide local status, browser login, cancellation, live bound-printer listing and local logout. Login accepts only the region and uses a short-lived loopback browser for credentials and verification codes; account tokens are not returned. Cached readiness does not prove live authentication. Cloud account use verifies the selected printer binding, and complete explicit cloud credentials take precedence; partial explicit credentials fail. Account login does not create or substitute for the application signing bundle, native SDK or FULU sessions. Logout removes the local session and does not claim remote revocation.

Managed user-token refresh is separate from application certificate renewal. Fresh login can retain private refresh material and an atomic generation; a durable pre-exchange journal prevents replay after an uncertain outcome. Existing access-only sessions remain usable but need a fresh sign-in to obtain refresh material. MCP requires an independent managed login; do not share HA's rotating refresh pair. Complete explicit credentials continue to take precedence until deliberately migrated. Cloud authority failures do not disable an independent LAN signed writer. Managed account locking requires Python 3 and POSIX `fcntl`; this managed flow is unsupported on Windows. An actual refresh exchange remains untested.

`account_cloud_print_history` accepts bounded `offset` and `limit` pages with printer filtering, a continuation and completeness evidence. `account_cloud_print_thumbnail` reads an owned task's validated image without returning its source URL. Pages are not an atomic snapshot.

`account_filament_manager` supports account filament configuration, pending matches, explicit create/update/delete, slot mapping with explicit bind or unbind per row, AMS sync and pending resolution. Calls are serialized and writes are not replayed. Treat `partial` and `unknown` as requiring inventory reconciliation before another write. AMS sync needs explicit slot and RFID identity and requests new spool creation only when selected. Live mutations remain unverified.

## Evidence and compatibility

The server provides `remote_upload_file`, `remote_delete_file`, `remote_archive_members` and `remote_archive_extract` tools. Upload requires explicit consent to possible internal history rotation; delete requires an exact fresh selection and confirmation. List and deletion are not atomic. Archive operations use bounded verified downloads; extracted members are data only and are not print authorization. A failed or interrupted mutation may have changed storage and is not automatically replayed. Remote write operations are not live-qualified; archive read qualification remains distinct from print authorization.

The optional remote camera/file tools use packaged direct TUTK networking, current account binding and application proof. They acquire the shared operation lock before minting one ticket and hold it until the request-owned connection and cleanup settle. No per-operation MQTT readiness watcher, duplicate prepare or separate helper service is required. `remote_camera_snapshot` returns one JPEG image, `remote_list_files` returns allowlisted metadata, and `remote_download_file` requires a workspace and returns checked artifact metadata. These tools require control scope because they establish remote media state and may publish local artifacts. Camera images are bounded to 4 MiB, downloads to 16 MiB and lists to 4,096 entries. Completed list and download CTRL frames are buffered until contiguous uint32 IDs, including wraparound; duplicates are ignored, gaps are not skipped or retried, and pending data is bounded to 16 frames and 16 MiB with a 4 MiB per-frame limit. Offsets, total size and terminal MD5 remain checked; camera takes the first complete keyframe. They do not provide continuous video or print authorization, and failures do not automatically remint. Normal camera, list and checked download reads passed on one selected printer; they do not establish print readiness or support for other firmware. See [remote camera and files](docs/TUTK.md).

Synthetic tests and mocked or local protocol checks do not establish live service authentication, device acceptance, a physical print or universal model/firmware support. The source repository declares GPL-2.0-only; do not incorporate AGPL code without a compatible licensing basis.

## Shared workspace and file exchange candidate

The optional printer artifact store and separate Orca workspace use the same opaque 43-character workspace ID with independent service-owned ledgers. Create on either service and explicitly cold-attach on the other; closing Orca releases its GUI, not project files. This coordinates one trusted operator and is not a hostile-tenant security boundary. `workspace_create`, `workspace_attach`, `workspace_status` and empty-only `workspace_delete` manage the printer-side ledger. `workspace_import_file` accepts an MCP file object (`openai/fileParams`) or any public HTTPS URL, including MakerWorld redirects to signed object storage. `workspace_upload_begin_https` returns one opaque, one-use raw PUT URL for a declared filename, byte length and SHA-256; a client uploads bytes directly then calls `workspace_upload_finish`. It never interprets a client-local path as server-local or requires base64. Existing begin/chunk/finish/abort provide bounded client-driven upload. Artifact info/read/delete use workspace and artifact IDs; `workspace_adopt_export` verifies a finalized Orca receipt and copies its exact bytes into the printer store. A completed artifact returns a server-local `file_path` for existing inspection, upload and print tools; staging is not inspection or print authorization.

The store is enabled by `BAMBU_ARTIFACT_DIR`. `BAMBU_ARTIFACT_OUTBOX_DIR`, `BAMBU_ARTIFACT_GROUP_GID`, `BAMBU_ARTIFACT_MAX_FILE_BYTES`, `BAMBU_ARTIFACT_MAX_TOTAL_BYTES`, `BAMBU_ARTIFACT_MAX_SLOTS`, `BAMBU_ARTIFACT_MAX_WORKSPACES`, `BAMBU_ARTIFACT_UPLOAD_IDLE_SECONDS`, `BAMBU_ARTIFACT_UPLOAD_HARD_SECONDS`, `BAMBU_ARTIFACT_UPLOAD_BASE_URL` and optional `BAMBU_ARTIFACT_TRUSTED_HOSTS` configure exchange, bounds, leases, fixed public upload origin and an optional literal-host download restriction. With no restriction, any public HTTPS source is accepted. The upload base is deployment-owned (for example `https://mcp.adamcoulter.au/3d-printing`), never inferred from Host. URL imports validate HTTPS, public DNS/IPs and every redirect; raw upload capabilities are stored only as a digest, are one-use and expire after 15 minutes. The service must not expose a capability after its initial tool response or raw download errors.

URL imports buffer up to two files per process, each up to the configured file limit (128 MiB by default), with additional temporary copies possible; memory use is not flat. Store coordination requires Python 3 and POSIX `fcntl` locking on a supported local filesystem. No cross-host or network-filesystem locking guarantee is made. Completed work is never automatically garbage-collected.

`workspace_export_print_plates` is the preferred Orca-to-printer handoff for selected sliced plates. It exports each requested zero-based source plate separately as a `sliced_3mf`, waits for the GUI to become idle, and requires the archive to contain exactly that source plate's `Metadata/plate_N.gcode` with nonempty matching `filament_ids`. Its receipt records both the requested source plate index and the same zero-based `artifact_plate_index`, which is the value passed to the printer service's inspection tools. A failed or malformed plate is returned explicitly without inventing an assignment; if Orca cannot establish that an export settled, or its bounded 105-second composite request deadline is reached, later requested plates are not attempted. It does not inspect, upload or dispatch any print.
The pinned native Orca control limits each wait to 50 seconds, and the handoff schema enforces that bound before it calls the GUI.

`workspace_publish_file` remains the lower-level path for a completed export from `/artifacts/<workspace_id>/<relative_path>`; it accepts only that workspace-relative path and cannot read a private project, checkpoint or arbitrary server file. Printer adoption checks ID, size, hash and file safety before publishing. Share only the Node published subtree read-only with Orca at the same absolute path, and the outbox read-write with Orca and read-only with Node. Use a verified dedicated supplementary artifact group; never share private homes, keys, printer credentials or IPC groups. Existing inspection and physical safety gates remain authoritative. Client attachment upload and a fresh-client authenticated slicer invocation remain separate verification gates.

The current candidate has isolated Node suite and installed npm/MCPB workspace coverage, and its Orca fixture passed all 56 tests on Linux without network access. An isolated trial verified a shared read-only input mount, X2D slice, outbox publication and hash-matched Node adoption; file-only inspection did not authorize dispatch. A later actual-image run verified clean closes and same-ID restore; an earlier failed close remains historically unexplained. The isolated trial does not establish a working user-client attachment handoff.
