# Integration interface

This repository owns the Bambu-only MCP server, its tools and Bambu printer, slicer and native-helper integrations. It does not own printer firmware, Bambu account services, installed vendor software or client applications.

## MCP and agent discovery

Clients connect over stdio or streamable HTTP. Stdout carries only MCP protocol messages; diagnostics go to stderr. Tool definitions and schemas describe their arguments and model-specific availability. `get_agent_guide` serves a task index and focused topics, including signing and printing, to tools-only clients; `bambu://workflow/` resources serve the same guide text. The signing guide supplies optional configuration descriptors, including a secret marker, without configured values. `get_agent_readiness` returns local configuration and capability states, named blockers and next actions with `dispatch_authorized: false`; it performs no live printer or physical readiness check.

Streamable HTTP uses one process-owned backend and transient protocol contexts for active requests, with no resident idle client session map. Legacy initialization returns client-held HMAC-signed compatibility metadata containing protocol version, capabilities, client information and a nonce. It is not an idle lease: restarting the process rotates its signing key and invalidates old tickets. `GET` and `DELETE` return 405 with `Allow: POST, OPTIONS`; DELETE does not revoke a ticket. Request cancellation or connection loss revokes the affected active operation's authority, not the shared backend or its job monitor.

The modern HTTP path uses the MCP SDK's native request handling. An opaque, signed, one-use continuation retains only active operation state during human input, with a 10-minute input wait and 30-minute operation deadline; confirmation resumes the same handler, never replays the physical operation. Both protocol paths share a 128-active-operation bound and reserved control capacity. After abort, handlers have 30 seconds to settle before fail-stop if they do not cooperate; this does not prove a dispatched mutation was undone. Shutdown waits up to 4.5 seconds for actual handlers before backend cleanup; otherwise the process exits with outcomes potentially unknown. No per-agent backend or additional service is required.

HTTP validates Host, Origin and optional static bearer authentication and bounds request bodies. OAuth authorization, token validation and discovery, TLS termination, and a secure proxy are deployment responsibilities; the server is not an OAuth provider. Non-loopback requires bearer authentication and separate TLS protection. An explicit Host allowlist is recommended for every non-loopback bind and required for hostname or wildcard binds; a literal IP bind otherwise enforces its exact Host. `MCP_HTTP_STATEFUL` must be absent or false; true and invalid boolean values fail startup. `MCP_HTTP_JSON_RESPONSE` prefers JSON for initialization and discovery while interactive calls can use SSE.

`bambu-printer-mcp-http-client` is a legacy stdio-to-HTTP relay using a private bearer-token file and HTTPS or loopback HTTP; it never starts or cleans up the backend. It declines `server/discover` so the host can fall back to legacy discovery. The relay retains a bounded initialization contract and, after a confirmed 404, may reinitialize and retry only discovery lists or ping when safe. It never automatically replays `tools/call`; check state before manually retrying an uncertain operation. Authentication and capacity errors use sanitized diagnostics.

`counterpart/1` remains a separate existing contract. The existing `counterpart_setup_fields` schema and field roles are unchanged. Changes to public tools, printer models, status semantics or `counterpart/1` require owner review and downstream impact analysis.

## Separate Orca workspace candidate

The independently deployable Orca candidate exposes `/3d-printing/slicer` through an authenticated proxy and a private Unix socket. It targets the official `feature/mcp` source at `8cccdf82d00381942d9b664750457da318e7d068`, including X2D profiles and full upstream MCP tools. Its separate image and upstream license do not change the printer server's ownership or license. The container uses `network_mode: none`; it receives no printer credentials and cannot directly reach a printer. Authentication and TLS belong to the proxy, and the gateway uses its own private bearer token.

`workspace_create` returns a durable opaque ID without starting a GUI. `workspace_open` selects that ID for the single GUI worker; native calls include the ID. `workspace_status` reports the worker and known workspace state, and `workspace_close` attempts a verified checkpoint before releasing the worker. IDs, profile data and artifacts persist across client and server restarts; an unclean stop or failed checkpoint requires recovery rather than an assumed restore. There are no per-agent protocol sessions. Workspace IDs coordinate one trusted operator and are not tenant-security boundaries. Expiry revokes access; unfinished outcomes remain unknown and are not replayed. Exclusive socket ownership and shutdown settlement prevent another worker from starting while the previous one is still owned.

The independently reviewed runtime candidate passed all 35 tests in an isolated, non-root Linux environment without network access. This interface is a candidate, not a claim of a running slicer: the source build, runtime image, real metadata, X2D slice/export/restore and client qualification remain pending. See [deploy/orca/README.txt](deploy/orca/README.txt) for configuration and validation limits.

## Printer operations and optional authentication

The explicit `connection_mode: "signed_mqtt"` print route uses inspected 3MF projects, including `.gcode.3mf`, and an operator-configured signer plus an absolute `BAMBU_PRINTER_TLS_CA_FILE` for direct printer storage TLS. It checks capability and a unique internal-storage name, uploads and requires a terminal acknowledgement, then reads the file back and checks its size and SHA-256 against the checked local artifact before final fresh preflight and signed MQTT dispatch using the selected local or cloud writer. Unsupported capability, mapping, trust or transfer fails closed. No automatic print replay, route fallback or file deletion is promised; post-publication failures can leave dispatch uncertain. `upload_file` provides 3MF upload-only on this route; `upload_gcode`, a raw G-code API, refuses it. Legacy routes retain their own formats. Model and firmware support is capability-dependent, not universal. Focused fixtures and one private X2D trial support this route: upload readback matched, and a signed-cloud job on firmware 01.02.00.00 reached FINISH with camera evidence of first-layer deposition and the completed fixture on the plate. Hands-on physical quality and fit remain unverified; other models and firmware are not qualified. This does not qualify the separate native-helper route. The four-client audit remains required before an upstream PR.

`get_agent_readiness` describes the default signed print selection and whether an absolute CA path is configured; it does not validate that file, a TLS session or physical readiness. A per-call route can differ from the default.

`get_printer_status` preserves display status when `fresh` is omitted or false. With `fresh: true`, it uses the shared backend to request new MQTT status and version reports and requires observed model identity and a printer-returned serial matching the configured target. It returns `observedSerial`, raw telemetry and request/receipt timestamps; missing identity, mismatched serials and timeouts fail without cached or configured identity substitution. This read-only telemetry is not complete print preflight or dispatch authorization.

Printer status and commands use MQTT; supported file transfers use FTPS or a separate native route. Printing retains inspection of the exact dispatched snapshot and selected plate, fresh printer safety checks and existing human-authorization semantics. Upload and dispatch are separate; a publisher acknowledgement or helper receipt does not establish device acceptance or physical success. Uncertain dispatches are not automatically replayed.

Fresh safety collection has an overall 15-second deadline covering connection and concurrent disconnection; both the MQTT transport connection timeout and its outer connection deadline are 10 seconds, disconnection drain is bounded to 5 seconds, and collection to at most 5 seconds of the remaining budget. Typed MQTT connection failures carry allowlisted `connection_diagnostics`; native and bridge print failures from their initial or confirmation safety reads also identify `safety_stage`. These diagnostics do not expose credentials or raw transport messages, and they do not trigger a retry. Native helper execution defaults to 230 seconds, with kill escalation after one second. These limits do not bound preceding slicing or inspection. Monotonic expiry prevents late asynchronous safety completion from recording or authorizing a dispatch; bookkeeping occurs synchronously at the final authorization boundary. Existing errors retain bounded, allowlisted `native_diagnostics` and preserve stable known refusal codes when available. Success requires an exact, unambiguous successful receipt for the latest authorized attempt. A client deadline or missing helper receipt does not establish whether dispatch occurred; a missing or pruned flight record is inconclusive. Failures after authorization remain uncertain unless there is an explicit rejection, and uncertain dispatches are not automatically replayed.

Signed controls are opt-in with explicit local or cloud transport and require an operator-provided application key, certificate chain and current CRL, independently configured device CA, OpenSSL 3 and a private initialized persistent sequence store. Optional local broker TLS trust is a separate boundary. Selected signed controls fail closed if prerequisites fail; signed project dispatch does not upload files, and legacy `gcode_file` dispatch is blocked on that route. The typed LED protocol has its own deterministic unsigned route, not a fallback from failed signing. Counter reservations cover only processes using the same store, not other applications or hosts.

Optional account tools provide local status, browser login, cancellation, live bound-printer listing and local logout. Login accepts only the region and uses a short-lived loopback browser for credentials and verification codes; account tokens are not returned. Cached readiness does not prove live authentication. Cloud account use verifies the selected printer binding, and complete explicit cloud credentials take precedence; partial explicit credentials fail. Account login does not create or substitute for the application signing bundle, native SDK or FULU sessions. Logout removes the local session and does not claim remote revocation.
