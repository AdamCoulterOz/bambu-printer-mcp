# Current context

## Purpose and state

This Bambu-only MCP server provides printer, slicing, model and print-monitoring workflows over stdio or streamable HTTP. It originated from upstream `main` at `4cadc9f7c84138382f215b3e254094fa66c6a689` (version `1.1.94`). Preserve the upstream safety and release rules in [AGENTS.md](AGENTS.md). The current feature work is unmerged and unpublished.

The unmerged HTTP work uses stateless per-request protocol contexts over one shared printer backend, with no idle per-client session pool. Legacy clients hold signed compatibility metadata; modern clients use the native HTTP protocol and bounded continuations for active human-input operations. Cancellation and cleanup are operation-scoped and do not close process-owned resources. Use a private service with bearer-token file authentication; the stdio adapter is only a relay. `MCP_HTTP_STATEFUL` must be absent or false. The Mac writer is disabled and its final counter state transferred. The managed Linux Node backend now exposes 92 tools; authenticated printer readiness and workspace status succeeded with the store configured and empty, without dispatch. A bounded signed part-fan trial succeeded as described below; wider control and print readiness remain unqualified.

Optional signed MQTT control supports explicitly selected local and cloud routes. It uses operator-supplied application signing material, independently configured device trust and a durable local counter. The account integration is separately opt-in; its browser flow provides a private cached session for the optional cloud route. Native SDK/FULU sessions remain separate from account login and signing. The candidate explicit signed_mqtt route combines independently verified direct internal-storage 3MF transfer with the existing signer; signing itself is not file transfer. Route and model support are not universal.

The signed_mqtt route has been privately deployed and exercised on one X2D: an upload-only request completed with matching full readback, and a subsequent signed-cloud print reached FINISH on firmware 01.02.00.00; camera images showed first-layer deposition and the completed fixture on the plate. Hands-on physical quality and fit remain unverified; other models and firmware are unqualified. Focused synthetic and MCP fixtures also cover the candidate; the private native SDK -26 readiness refusal is a separate gate, not evidence that the recovered application signing keys are invalid. Four Scan-to-Make client audits remain required before an upstream PR; the user-approved private deployment exception is not a release.

Agent guidance is available from initialization instructions, `get_agent_guide` and `bambu://workflow/` resources. `get_agent_readiness` reports only known local configuration and capabilities; unknown remains unknown. The existing `counterpart/1` setup schema is unchanged.

`get_printer_status({fresh:true})` provides read-only fresh MQTT identity/state/error telemetry through the same shared backend and requires a matching returned serial. Default display status is unchanged. This identity probe does not qualify full print readiness.

An in-memory MQTT fixture reproduced a 2-second transport deadline expiring before a 2.5-second CONNACK; the transport deadline now matches the 10-second connection bound. This reproduces a failure mechanism, not proof of the cause of the private print attempt. Native/bridge print preflight exposes sanitized connection diagnostics and identifies the initial or confirmation safety stage without retrying.

Native-print safety collection and helper execution have bounded deadlines. Expired requests cannot authorize a late dispatch, and helper errors retain allowlisted diagnostics. The native-helper deadline is not an end-to-end limit on slicing or inspection. Focused fixtures and independent review cover the repair; native physical printing remains unqualified.

## Shared workspace and file exchange candidate

An optional Node-managed artifact store and separate Orca workspace use the same explicitly attached opaque ID, independent ledgers and data-only published/outbox mounts. Node handles bounded client-file import or chunk staging and verifies Orca export receipts; the returned server-local path enters the existing inspection/print workflow. Closing the Orca worker does not delete files; completed work persists until explicit deletion. The managed services and data-only mounts are deployed. The user reports both plugin connections established; public slicer tool invocation and an actual client attachment handoff remain unverified. See [INTERFACE.md](INTERFACE.md) for the candidate contract and limits.

An isolated cross-service trial staged a 684-byte cube, read it through the shared read-only mount, sliced it with the X2D 0.4 mm and BBL PLA presets, and published and adopted the 55,837-byte 3MF with matching SHA-256 `25341814d1c311409c2548bd15db5a9f1ccff34d52b9ab0bc08e05a8e07a82cc`. ## Invariants

- Preserve exact-file and selected-plate inspection, fresh observed identity, nozzle, state and safety checks on print paths. File-only inspection and local configuration do not authorize dispatch.
- Act on the person's specific print request and retain existing elicitation rules. File upload, a dispatch receipt, observed job progress and physical print success are distinct evidence.
- Signed operation fails closed on missing or invalid prerequisites; never automatically fall back or replay an uncertain dispatch. Local counter reservations coordinate only processes sharing that state directory, not independent controllers.
- Browser login takes passwords and verification codes only through the temporary loopback flow. Never return account tokens or expose credentials in source, logs or tool results. Account status reports cached state, not live authentication.
- Preserve Bambu-only scope, existing public contracts, upstream authorship and licenses. Do not contact a printer during routine development.

## Separate Orca runtime

The runtime candidate launches each Orca GUI under a private D-Bus session runner in the harness-owned process group. The recorded launch identity is the runner, not a public GUI PID. The actual image verified the runner, private bus and GUI in one process group and Xvfb separately, with clean checkpoint, restore and final cleanup. Earlier close failures remain unexplained. Process snapshots skip entries that disappear with ENOENT or ESRCH during enumeration; all other snapshot failures remain fail-closed. The original close failure's errno was not captured.

The selected official `feature/mcp` source is commit `8cccdf82d00381942d9b664750457da318e7d068`, with X2D profiles and full MCP. After the earlier packaging failure, corrected source CI run `43995773386` succeeded and produced a verified bundle with SHA-256 prefix `57508f`. The separately licensed runtime candidate under `deploy/orca/` has passed independent source review. It uses durable explicit workspace IDs, stateless MCP requests and one cold-on-idle GUI worker, with checkpoint and recovery state. It is for one trusted operator, not tenant isolation; `network_mode: none` and a Unix socket gateway prevent direct printer egress. The public proxy route `/3d-printing/slicer` is deployed with separately scoped OAuth.

After an initial missing-locale modal, the corrected runtime image reached readiness in about 31.8 seconds with locale, OpenGL and permissions checks passing. Its catalog exposed 57 tools; legacy and modern clients both returned ready with the exact X2D 0.4 mm and BBL PLA presets, no jobs or dialogs and one GUI worker. The isolated slice and transfer passed as described above. The uninstrumented runtime image `3fddb1d70090cc0042aa7c93f0319479a1c911c474c2ae22bab54b39e7798376` passed startup, checkpoint, restore and cleanup. A final guide-only Node image exposed 92 tools with unchanged schemas and the portable guide. The managed Node and Orca images are deployed. Public TLS-protected OAuth metadata for both resources passed, and the user reports both connections established in the private 0.1.1 plugin. The current Codex session has not loaded the slicer tools, so a fresh client session and actual authenticated slicer invocation remain unverified. Global Codex and Claude Code user configuration now include the slicer HTTP endpoint; their OAuth and loaded-tool checks remain pending.

There is no supported global inventory proving all MCP operations have drained before replacing the backend. SIGTERM cancels operations and waits briefly for settlement; it is not a passive drain, and uncertain outcomes must not be replayed automatically.
