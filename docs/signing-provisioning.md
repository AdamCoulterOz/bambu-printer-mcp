# Optional signing credential provisioning

Signed control is opt-in. The existing `BAMBU_SIGNING_DIR` may contain the three manually supplied PEM files, or a managed credential generation produced by the explicit setup tool. The private application credentials do not replace the separately configured device CA or the independently initialized durable sequence store. Neither setup nor renewal contacts a printer or uses an account token.

The one-click route uses `BAMBU_SIGNING_BOOTSTRAP_ENABLED=true`, an absolute private `BAMBU_SIGNING_DIR`, and `account_setup_signing` with `region` and optional `method: "automatic"`. It downloads the fixed [official Bambu Handy 4.4.1 package](https://public-cdn.bblmw.cn/upgrade/app/software/4.4.1/app_zh_release.apk) (185,964,655 bytes) to a private temporary file, verifies the full size and hash, and removes the package after extraction. The vendor [download page](https://bambulab.cn/zh-cn/download) links this package. This automatic acquisition path has not been live-qualified. The download can take several minutes, has no percentage progress display, and requires network access; a changed package, redirect, timeout or cancellation fails closed. No local APK, secret or account login is needed for this route. The installed workflow can also extract an operator-supplied Bambu Handy 4.4.1 APK. Both routes accept only the previously examined APK SHA-256 `88548d4d993741e95727d1675e8d997bb92586f732f1ef72ada0281921f76506`; the integration does not embed the bootstrap. Extraction verifies the bootstrap and certificate fingerprints and writes private local files. It needs `unzip`; issuance serialization needs `python3` with POSIX `fcntl`, and verification needs OpenSSL 3 or newer. Managed account locking likewise requires Python 3 and POSIX `fcntl`; the managed flow is unsupported on Windows. Keep the source and managed directories owner-only and writable by the server process. Do not commit the APK, bootstrap, signing key, generated files or request URLs.

The source evidence is Android decompiled `defpackage/c68.java` cases 64–66, `paq.java`, `o9j.java` and `hre.java` for the generated bootstrap mapping; `com/bambulab/bambulab/network/auth/iot/IotApi.java` for the credential GET; and `IotCertManager.java` and `IotCertConstants.java` for the request and response path and wrapping certificate. The bootstrap string SHA-256 is `0711bdbef23b3f59dcb8eb3d6b04d0e0cb9d22425c4015b6c0a726eae1359ae3`; wrapping-certificate DER SHA-256 is `2a5e9b8fd6a3b3642b5d9f4d1fd1cd354d0d5cb2caa76e66ed76f2bb97a6d5bb`. The directly issuing application CA is independently pinned at `0569df45e97c9e5b3ea1eaa0c73b0d1f65f33579f1542870ec5845a134747978`.

Android calls packed native crypto routines whose implementations were not recovered. One independent authorized vendor issuance demonstrated interoperability with AES-256-GCM request framing (12-byte IV, ciphertext, 16-byte tag), RSA PKCS#1 v1.5 wrapping of the random AES key, padded URL-safe base64, and an AES-GCM encrypted response key. It returned a certificate string, encrypted key string and an array containing one CRL. This is evidence for that issuance, not proof of every vendor client version or printer compatibility. The returned leaf, pinned issuer, key match, CRL signature, revocation and validity are verified before a generation is activated. CRL coverage is for the directly pinned issuer; it does not establish upstream revocation coverage.

For automatic on-demand renewal, configure the server with:

- `BAMBU_SIGNING_DIR`: the absolute private managed directory, also used for signed control.
- `BAMBU_SIGNING_AUTO_RENEW=true`: explicitly enable renewal before a signed operation.
- For manually supplied source files, set both `BAMBU_SIGNING_BOOTSTRAP_FILE` and `BAMBU_SIGNING_WRAPPING_CERTIFICATE_FILE` to their absolute private paths. For APK-based setup, omit both: the source is stored privately within each published generation.
- `BAMBU_SIGNING_REGION`: `global` or `cn`, selecting one fixed vendor HTTPS endpoint.

For a supplied APK, set `BAMBU_SIGNING_SOURCE_APK` to its absolute private path and call the tool with `method: "apk"`; for private source files use `method: "files"`. If `method` is omitted, configured sources retain precedence and automatic acquisition is selected only when none is configured. The temporary package and extraction are removed after issuance; the verified source is retained with the managed generation for renewal, and no source paths are returned. Keep the existing signed-control selection, device trust and sequence-store settings as well. Without automatic renewal, issue or renew explicitly; existing direct PEM installations continue to work. With it enabled, the server attempts renewal when the certificate or CRL has seven days or less remaining. Automatic attempts are durably limited to one per 24 hours; they do not retry or switch endpoints. If renewal fails, an independently revalidated current generation remains usable while valid. Missing, expired, revoked or otherwise invalid material fails closed. Generations are retained so an in-flight session can finish loading its chosen snapshot. Automatic renewal happens on demand, not on a background schedule; an idle server may not renew before expiry.

Cooperating managed issuers use a stable OS-held lock and an atomic current-generation switch. A changed pointer aborts publication. Filesystem writers that bypass the lock can race the final pointer check; do not edit or replace a managed generation concurrently. The sequence counter is separate and is never reset or rotated by credential provisioning.

The separate user-account refresh route journals its exchange before handoff and atomically publishes a verified account generation. An existing access-only session needs a fresh sign-in to obtain refresh material. An uncertain exchange requires reauthentication; writes are not replayed. This is distinct from application-credential renewal; an actual account refresh exchange has not been live-tested.
