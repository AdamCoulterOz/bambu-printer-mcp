# Printer and slicer workflow

## Discover and plan

Use the configured hosted printer and slicer connectors when present; their names and endpoints are host-specific. Common names are `printer` and `slicer` in the plugin, and `bambu-printer-mcp` and `bambu-slicer` in Claude; discover the actual connected services. Discover tools and actual schemas rather than inventing names or assuming a local application. Read the printer's `get_agent_guide` for relevant topics and `get_agent_readiness` if available. Readiness does not establish live or physical readiness. If a connector is unavailable or needs sign-in, report the missing capability and use that host's connection flow.

For monitoring and current identity, use fresh compact status where supported: `get_printer_status({fresh:true, detail:"compact"})`; use `detail:"full"` for diagnostic detail. An older deployment may lack `detail`; check its schema and use the supported fresh identity read, with full details only when that evidence is needed. Fresh status does not substitute for the current printer preflight. Identify the requested printer, model, nozzle, plate, material and available physical feeds from user input and observations. Do not infer a model or assume a ready bed from a cached status.

Use `get_filament_inventory` where available. Keep account reels, printer-reported slots, unmatched printer observations and unidentified holders distinct. Library retrieval and printer state may be incomplete or stale. Treat account-reported `not_loaded`, weights and remaining percentages as source reports, not physical measurements. Use an explicit deterministic physical slot/spool assignment from the user or a unique exact RFID/roll UUID match, checking the source and ambiguity. A cloud-reported location is an account observation, not a current MQTT identity match; it can conflict or be stale. Never join reels or infer stored location by material, colour or similar names; an unidentified holder may be a library reel, so do not double-count it. Ask for unresolved physical mapping when necessary for the requested print.

## Shared workspace and transfer

1. Call `workspace_create` on either service, then explicitly cold-attach the same opaque workspace ID on the other using `workspace_attach`. Each owns a separate ledger. Reuse the user's existing workspace for follow-up. Call `workspace_open` on the slicer when required and pass the ID to each native Orca call according to its schema. Preserve existing work and unsaved settings.
2. A client attachment's local path is not a server path. Use `workspace_import_file` for the printer workspace’s supported file object or allowed HTTPS source, or use `workspace_upload_begin`, ordered `workspace_upload_chunk` calls and `workspace_upload_finish` for available bytes with the advertised order, encoding and integrity fields. Use the completed receipt. Pass its returned server path to Orca only if the published subtree is mounted there at the same path; do not invent a path or assume a mount.
3. Discover the actual load, arrange, preset, slice, wait and export schemas. Select the intended model, nozzle, material and plate; preserve existing settings unless the request warrants changes. Check slice warnings, preview and estimated time and material. A running or dialog-blocked job is not a reason to repeat it; inspect its state and wait or resolve the dialog when appropriate.
4. After export completes, call `workspace_publish_file` on the slicer for the workspace-relative artifact. Call `workspace_adopt_export` on the printer service with the finalized receipt’s workspace ID, export ID, SHA-256 and size. Inspect the adopted artifact at the returned printer path and selected plate. Transfer, slicing and inspection alone do not authorize dispatch.
5. Checkpoint or call `workspace_close` on the slicer workspace when appropriate; closing releases the worker and preserves completed files, not a deletion request. If checkpoint or operation outcome is uncertain, report it, retain the workspace, inspect `workspace_status` and do not replay automatically.

## Physical operation

A request to prepare, slice or inspect does not request dispatch. For an actual print request, identify the exact inspected artifact and revision, plate, printer, nozzle, material and complete physical feed mapping; use the current printer guide and required preflight and confirmation flow. Do not bypass the printer service's validator or safety checks. If a dispatch or control outcome is uncertain, inspect current state and report uncertainty before any retry. Slice estimates, upload receipts and running status do not prove first layer, finished quality or fit.

For geometry-sensitive quality questions, read [quality.md](quality.md). For Orca operations and their version-specific references, read [orca/guide.md](orca/guide.md).
